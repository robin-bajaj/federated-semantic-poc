# Federated dbt Semantic Layer POC

Team A (Equity) and Team C (Fixed Income) independently author position models and opt into the CDO-governed `cdo.position` v1 contract. The [CDO governance repository](https://github.com/robin-bajaj/cdo-semantic-governance) owns the contract, pre-parse inheritance compiler and validation rules. Custom `semantic_inheritance.extends` metadata is **not native dbt syntax**; it must be compiled before dbt parses or deploys the models.

## CDO Position snapshot lifecycle

1. **Team PR validation:** `.github/workflows/cdo-semantic-ci.yml` runs when Team A/C proposes changes to `main`. It compiles opted-in team inheritance using the pinned CDO governance package, validates required fields/metrics and dbt parsing, and builds staging models with enforced native contracts against isolated Neon CI schema for same-repo PRs.
2. **Pre-merge snapshot — Sync called by CI:** On successful validation, CI calls **`.github/workflows/sync-cdo-position-snapshot.yml` directly** with the exact team PR head commit. Sync compiles + composes via the governance package, runs `meta_context_validator.generate_cdo_dbt`, and produces native SQL/YAML. A read-only generator job hands these files to a separate publishing job. For same-repo PRs, it commits the resulting candidate to an isolated `automation/cdo-position-pr-N` branch; for forks, it retains the artifact only. The team PR is still unmerged. There is **no second generator workflow**.
3. **After team merge — Sync:** A team semantic change pushed to `main` triggers the same Sync workflow using approved source. It regenerates the complete CDO snapshot and, if different from `main`, creates or updates `automation/sync-cdo-position-snapshot` and opens the official CDO review PR. Candidate branches are never the approved snapshot and are not automatically merged.
4. **After CDO approval — Release:** CDO reviewers approve the generated SQL/YAML PR into `main`. `.github/workflows/cdo-semantic-release.yml` re-generates from approved sources with the **governance-owned** generator, checks the committed files match, then builds the CDO view and upstream team relations in the Neon release schema.
5. **Publish — manual:** `.github/workflows/publish-compiled-semantic-models.yml` compiles deployment-ready team semantic YAML from `main` into `generated/production`. It carries the already reviewed CDO SQL/YAML from `main` and does not itself deploy dbt Cloud.
6. **Hosted dbt / Tableau:** Run the hosted dbt Cloud deployment job that uses `generated/production`, then query/refresh the Semantic Layer through Tableau.

**CDO-generated artifacts in the federated project:** `models/semantic_models/team_cdo/generated/cdo_enterprise_positions.sql` and `.yml`. The **intermediate** `/tmp/current_cdo_catalog.yml` is generated by governance `compose_cdo` as input to governance `generate_cdo_dbt` and is **not** persisted in the governance repository.

**Pre-merge safety:** Sync's generator job has read-only repository permissions. The separate Git-writing job checks out trusted `main` and does not execute code from the unmerged PR. Unmerged candidates use PR-specific branches; only approved `main` changes can cause the official CDO snapshot review PR.

**Ownership:** Team A/C own authored SQL, local semantic fields and metrics. CDO owns its common Position contract and approves generated CDO semantics. The CDO governance package owns native CDO generation logic; the federated dbt project owns the reviewed executable SQL/YAML snapshot. The CDO snapshot is versioned through Git commits on `main`, not through independently maintained snapshots.

**Governance consistency:** CI, Sync, Release and Publish use reviewed CDO governance commit `dbcddc0cf58d05d393f95943ae954577c2e0957b`. Update all four references together after a reviewed governance change.
